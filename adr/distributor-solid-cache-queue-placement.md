# ADR: Placement of Solid Cache / Solid Queue and application-specific DB

Status: superseded by `four-app-solid-cache-and-solid-queue.md`

Superseded on: 2026-04-23

**Status:** Historical plan (2026-04-23)

**Scope:** distributor / foundation / identity / zenith 4 apps (Solid Queue actual use is also
related to lib)

## Context

Solid Cache / Solid Queue is currently:

- **Migration is repository root share**: `db/caches_migrate/`, `db/queues_migrate/`
- **DB name is already branched by application** (e.g. `development_distributor_cache_db`,
  `development_foundation_queue_db`)
- \*\*schema snapshot only `<app>/db/cache_schema.rb`, `<app>/db/queue_schema.rb` Exists under each
  app as
- Solid Cache side is still `:solid_cache_store` (mainly memory_store/null_store) and only the DB is
  prepared.
- Solid Queue is `lib/config/application.rb` and `config.active_job.queue_adapter = :solid_queue` /
  Connection name `queue` as
  `connects_to = { database: { writing: :queue, reading: :queue_replica } }` See

This configuration has the following distortions:

1. Although the migration is shared by the root, the DB is separate for each application, so it is
   unclear which app's DB this migration should be sent to.
2. The connection names `cache` / `queue` are generic and Solid Cache / Solid It is difficult to
   tell at a glance that it is a Queue-specific resource.
3. In the case of a distributor, the cache/job worker should be exclusive to the app, but if the
   naming is ambiguous, the scope is likely to collapse in the future.

Goal: Solid Cache / Solid Organize the Queue placement according to the application, unify the names
with the Solid prefix, and bring migration under the application.

## Final Design

### 1. Rename DB name

Changes below for each app:

| Old DB name                        | New DB name                              |
| ---------------------------------- | ---------------------------------------- |
| `development_distributor_cache_db` | `development_distributor_solid_cache_db` |
| `development_distributor_queue_db` | `development_distributor_solid_queue_db` |
| `development_foundation_cache_db`  | `development_foundation_solid_cache_db`  |
| `development_foundation_queue_db`  | `development_foundation_solid_queue_db`  |
| `development_identity_cache_db`    | `development_identity_solid_cache_db`    |
| `development_identity_queue_db`    | `development_identity_solid_queue_db`    |
| `development_zenith_cache_db`      | `development_zenith_solid_cache_db`      |
| `development_zenith_queue_db`      | `development_zenith_solid_queue_db`      |

Same change pattern for test/production environments.

### 2. Rename database.yml connection name and ENV

- Connection name: `cache` → `solid_cache`, `cache_replica` → `solid_cache_replica`, `queue` →
  `solid_queue`, `queue_replica` → `solid_queue_replica`
- ENV: `POSTGRESQL_CACHE_PUB/SUB` → `POSTGRESQL_SOLID_CACHE_PUB/SUB`, `POSTGRESQL_QUEUE_PUB/SUB` →
  `POSTGRESQL_SOLID_QUEUE_PUB/SUB`
- migrations_paths: `../db/caches_migrate` → `./db/solid_caches_migrate` (relative path under the
  app), similarly queue

Example of distributor (same format for other apps):

```yaml
development:
  solid_cache:
    <<: *default
    database: development_distributor_solid_cache_db
    host: <%= ENV["POSTGRESQL_SOLID_CACHE_PUB"] || default_host %>
    migrations_paths: db/solid_caches_migrate
  solid_cache_replica:
    <<: *default
    replica: true
    database: development_distributor_solid_cache_db
    host: <%= ENV["POSTGRESQL_SOLID_CACHE_SUB"] || default_host %>
    migrations_paths: db/solid_caches_migrate
  solid_queue:
    <<: *default
    database: development_distributor_solid_queue_db
    host: <%= ENV["POSTGRESQL_SOLID_QUEUE_PUB"] || default_host %>
    migrations_paths: db/solid_queues_migrate
  solid_queue_replica:
    <<: *default
    replica: true
    database: development_distributor_solid_queue_db
    host: <%= ENV["POSTGRESQL_SOLID_QUEUE_SUB"] || default_host %>
    migrations_paths: db/solid_queues_migrate
```

### 3. Migration placement

Move each app (`distributor`, `foundation`, `identity`, `zenith`) under:

- `distributor/db/solid_caches_migrate/20260312100000_create_solid_cache_entries.rb`
- `distributor/db/solid_queues_migrate/20251220094000_create_solid_queue_schema.rb`
- `distributor/db/solid_queues_migrate/20260309000001_convert_timestamps_to_timestamptz.rb`

Place (copy) the same file to foundation / identity / zenith.

Delete root `db/caches_migrate/` and `db/queues_migrate/`.

### 4. Rename schema snapshot

In each app:

- `<app>/db/cache_schema.rb` → `<app>/db/solid_cache_schema.rb`
- `<app>/db/queue_schema.rb` → `<app>/db/solid_queue_schema.rb`

The contents can be regenerated by running `bin/rails db:schema:dump`.

### 5. Solid Queue / Solid Cache configuration update

**`lib/config/application.rb`:**

```diff
- config.solid_queue.connects_to = { database: { writing: :queue, reading: :queue_replica } }
+ config.solid_queue.connects_to = { database: { writing: :solid_queue, reading: :solid_queue_replica } }
```

**`lib/config/environments/production.rb`:**

```diff
- config.solid_queue.connects_to = { database: { writing: :queue } }
+ config.solid_queue.connects_to = { database: { writing: :solid_queue } }
```

Replace in the same way if a similar definition exists in other apps.

**Solid Cache side** is currently Rails' `cache_store` Since it is not used as a server, only the
settings are changed and no wiring is required. Separate ADR when needed. Add
`config.cache_store = :solid_cache_store` + `connects_to` (at this time `solid_cache` (See
Connections).

### 6. config.yml for Solid Queue / Solid Cache

- No need to change the contents (max_age, etc.) of `lib/config/queue.yml`, `lib/config/cache.yml`
- However, it is necessary to decide whether to place a copy under each application or continue to
  refer to shared lib (see Open Items below)

### 7. Impact range check

- `distributor/config/puma.rb`, `foundation/config/puma.rb`, `identity/config/puma.rb`,
  `zenith/config/puma.rb`: `plugin :solid_queue` (The connection name is determined by
  application.rb, so there is no need to change it.)
- `lib/config/cache.yml` / `lib/config/queue.yml`: No change required
- Check if the DB name is written directly in the Docker compose/seed script

  Make sure there are no remaining

## Open Items (must be determined before implementation)

1. **Placement of config/queue.yml, config/cache.yml**: Currently `lib/config/` It is shared in the.
   If you want to switch to exclusive use of each app, copy it to `<app>/config/queue.yml` and use
   Solid There is also an option to allow each app to have Queue startup options. → Recommended:
   Keep the status quo (lib sharing). Personalize when needed.
2. **Migration copy vs symbolic link**: If you copy the migration with the same content to each
   application, Solid When a new migration is required due to a Cache/Queue gem update, it takes
   time to synchronize four locations. → Option A: Copy (simple, highly app-independent) → Choice B:
   `lib/db/solid_caches_migrate/` , and refer to the relative path from each app's database.yml →
   Recommended: A (copy) this time. Solid Since Cache/Queue schema changes are infrequent,
   application independence is prioritized.
3. **DB data transfer**: There is no problem in discarding the cache/queue contents of the
   development environment. Production has not yet been deployed.
4. **Actual usage status of identity/foundation/zenith**: `plugin :solid_queue` in puma.rb Yes, but
   check whether actual jobs are flowing (schedule/recurring settings) and understand the impact.
