# app/services Audit — Architecture Review

## 1. Executive Summary

`app/services` contains **230 files** across a wide spectrum of responsibilities. Roughly **60–70
files** (25–30%) do not belong there by the classification rule given. The problems cluster in five
categories:

1. **Pure value / constant holder files** that have no side effects, should be `app/values`.
2. **Policy / eligibility decision objects** that only evaluate rules and return booleans or raise,
   should be `app/policies`.
3. **Presenter-flavored objects** that format audit log entries for views, should be
   `app/presenters`.
4. **Minimal constant holders** (1–3 constants, no logic) that do not warrant their own file at all
   and should be inlined into their containing domain object or the contract module that owns them.
5. **Vague `-Service` suffixes** on classes that have real side effects and should remain but be
   renamed.

The ceremony subsystem (email, passkey, TOTP, telephone, social, step-up, secret credential) is the
single largest coherent body of services and is **correctly structured**. The
grant/result/consumer/issuer/committer/purger/replay-store naming convention is precise and
defensible. Do not disrupt it.

The OIDC subsystem is also largely correct — most files in that area coordinate multi-step side
effects.

The most actionable targets are the small pure modules and value objects scattered throughout.

---

## 2. Architectural Standard for This Codebase

Based on the code read:

- **`app/services`** is used as the primary bucket for all non-model, non-controller domain objects.
  It has grown to include pure value objects, policy predicates, protocol definitions, and constant
  holders alongside genuine services.
- **`app/values`** exists and is used for `Data.define`-style immutable objects. It is underused —
  several objects in `app/services` belong there.
- **`app/policies`** exists and is used (Pundit). Pure rule/eligibility evaluation that doesn't need
  Pundit can also go there as plain Ruby objects.
- **`app/queries`** exists. DB read-only builders should go here.
- **`app/presenters`** exists. View-facing formatters should go here.
- **`app/validators`** exists.
- **`app/forms`** exists.

Rails Zeitwerk autoloading (the framework Rails uses by default since Rails 6) derives the expected
constant name from the file path. Moving a file changes its constant name. Every move requires
updating all call sites. This is the primary risk and cost of any refactoring.

## 4. Ceremony Subsystem Pattern Assessment

The five ceremony families (email, passkey, TOTP, telephone, social, step-up, secret-credential) all
share the same 10-part structure:

- `*_contract.rb` — JWT claim schema constants + validation helpers
- `*_grant.rb` — typed JWT grant value object (issue/decode/validate)
- `*_result.rb` — typed JWT result value object
- `*_replay_store.rb` — DB repository (create_transaction!, find_transaction!)
- `*_result_issuer.rb` — issues signed JWT (reads DB to validate grant; crypto only)
- `*_result_consumer.rb` — decodes + marks transaction consumed (DB write)
- `*_final_committer.rb` — validates result + commits domain change (DB transaction + audit)
- `*_transaction_purger.rb` — batch deletes expired transactions
- `*_transaction.rb` — constant-only skeleton
- `*_candidate_store.rb` (where used) — stores ceremony candidate (DB write)

The naming is consistent, precise, and defensible. The **committers, replay stores, consumers,
purgers, and candidate stores** have genuine side effects and must remain in `app/services`. The
**contracts, grants, results, and transaction skeletons** are pure value objects and should move to
`app/values`, but doing so is a large mechanical change. Treat as Phase 2/3.

The `*_transaction.rb` skeleton files (`IdentityEmailCeremonyTransaction`,
`IdentityPasskeyCeremonyTransaction`, `IdentityTotpCeremonyTransaction`,
`IdentityStepUpCeremonyTransaction`) each contain only one or two constants. They should be inlined
into their contract module.

### 5.1 OidcClientRegistry (SHOULD MOVE → `app/queries`)

This is the authoritative client lookup layer for OIDC. Every move or rename here risks breaking
token validation across all surfaces. Do not rename during an active deploy or in the same PR as
behavior changes.

These encode/decode auth tokens. They are called in authentication hot paths. Moving them requires
Zeitwerk constant rename across ~15+ call sites. Risk: high. Benefit: clear. Do as an isolated PR
with no behavior change.

### 5.3 StepUpResolver (MUST MOVE → `app/policies`)

Called from `before_action` hooks and controller concerns. Renaming the constant requires a search
across all controller + concern call sites.

### 5.4 Sign::\*::Settings::ActivityLog (MUST MOVE → `app/presenters`)

These are used directly by controllers
(`@activity_log = Sign::App::Settings::ActivityLog.new(client)`). Moving to `app/presenters`

### 5.5 `health.rb` (SPLIT)

The monolithic `Health` module is referenced in health controllers and Puma initializers. Do not
split it without first confirming all call sites. Split only in an isolated refactor PR.

### Phase 5: Lock the Convention

**Rule for future PRs:**

A class may remain in `app/services` only if it does at least one of: database writes, external
HTTP/API calls, job dispatch, cache mutation, session/cookie mutation, token issuance with a side
effect, event emission, or multi-model orchestration across a transaction boundary.

**Suggested lint rule** (RuboCop custom cop or `app/services/.rubocop.yml`):

```ruby
# Heuristic: flag `module_function` or `Data.define` at top level in app/services
# These are strong signals the file belongs in app/values or app/policies
```

**Test requirements for every service:**

- At minimum one test that calls `#call` or the main entry point and confirms the expected side
  effect occurred (DB record created/updated, event emitted, token issued).
- Tests that verify `#call` is idempotent where claimed.
- No test should pass if all DB writes are removed from the implementation.

**PR review checklist addition:**

> Does this new service write to a database, make an HTTP call, enqueue a job, mutate session/cookie
> state, or orchestrate multiple models across a transaction boundary? If not, it does not belong in
> `app/services`.
